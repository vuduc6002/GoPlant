### 2. CHI TIẾT CÁC HẠNG MỤC TRIỂN KHAI (FIX A - G)

#### FIX A — Strict Distributed Lease Fencing
- **Cơ chế Token Sở hữu Độc quyền (Strict Token Ownership):**
  - Mọi thao tác cập nhật trạng thái dọn dẹp hoặc thất bại đều bắt buộc phải cung cấp lease token không rỗng.
  - Token truyền vào phải khớp chính xác với `reconcile_lease_token` đang được lưu trong cơ sở dữ liệu.
  - Nếu token là null, rỗng, hoặc không khớp với bản ghi: toàn bộ thao tác bị từ chối fail-closed, không thay đổi bất kỳ trường dữ liệu nào.
  - Ngăn chặn triệt để hiện tượng stale worker (worker quá hạn) ghi đè hoặc can nhiễu vào bản ghi của worker mới.
  - Áp dụng đồng bộ cho `completeReconciliationSuccess`, `recordReconciliationFailure`, `completeDelete`, và `recordDeleteFailure`.
- **Ràng buộc Máy trạng thái (State Validation):**
  - `completeReconciliationSuccess()` chỉ cho phép chuyển sang `DELETED` khi bản ghi đang ở trạng thái xử lý hợp lệ (`RECONCILING` hoặc `DELETING`), tuyệt đối không tác động lên `READY`, `ATTACHED`, `DELETED`, hoặc `FAILED`.
  - `recordReconciliationFailure()` chỉ áp dụng cho đúng lease owner và chỉ khi trạng thái là `RECONCILING` hoặc `DELETING`. Không bao giờ chuyển trạng thái `DELETED` thành `FAILED`.
- **Unique Lease Per Object:**
  - Trong `MediaReconciliationService`, loại bỏ việc dùng chung một token cho cả vòng lặp.
  - Mỗi bản ghi Media candidate được cấp một UUID lease token độc lập, truyền xuyên suốt qua chu trình: claim lease -> Storage HTTP delete -> DB complete/failure checkpoint.

#### FIX B — User DELETE và Reconciliation State Machine
- **Tái cấu trúc luồng xóa User DELETE:**
  - `DeleteDecision` được mở rộng mang theo `deleteToken` đại diện cho phiên xóa cụ thể.
  - `beginDelete()`: Khóa dòng bằng `findByIdForUpdate`. Nếu bản ghi đang ở trạng thái `READY`, chuyển sang `DELETING` và cấp lease 60 giây kèm token riêng.
  - Ràng buộc idempotent: Nếu media đang ở trạng thái `RECONCILING` hoặc `DELETING` với lease đang active, request xóa lặp từ người dùng được xử lý an toàn (idempotent no-op qua `DeleteDecision.ofAlreadyDeleted()`), không xóa lease token và không kích hoạt HTTP Storage delete độc lập cạnh tranh.
  - Bản ghi đang ở trạng thái `ATTACHED` tiếp tục bị chặn với HTTP 409 `MediaAttachedException`.
  - `completeDelete(mediaId, deleteToken)`: Chỉ cập nhật sang `DELETED` khi token khớp chính xác và trạng thái là `DELETING`.
  - `recordDeleteFailure(mediaId, deleteToken, errorMessage)`: Nếu xóa Storage thất bại, ghi nhận chi tiết lỗi đã làm sạch secret và xóa lease để worker reconciliation định kỳ tiếp quản retry.

#### FIX C — Real Concurrency Tests trên PostgreSQL & In-Memory Storage Simulator
- **In-Memory Storage Simulator (`InMemoryStorageSimulator`):**
  - Quản lý trạng thái thực tế của Storage bucket: hỗ trợ `put()`, `putDeferred()` (mô phỏng timeout nhưng Storage ghi muộn), `completeDeferred()`, `exists()`, và `delete()` (idempotent, trả về true nếu có object, false nếu 404).
  - Tích hợp kiểm tra lỗi mạng có kiểm soát (`setFailDeletes(true)`).
- **10 Kịch bản Real Concurrency Tests (`MediaReconciliationRaceTest`):**
  - Thực thi đa luồng qua `ExecutorService` và `CountDownLatch` trên PostgreSQL:
  1. *Race 1:* Hai worker tranh chấp claim cùng một Media đồng thời -> Đúng một worker chiếm được lease, worker còn lại nhận null.
  2. *Race 2:* Worker A hết hạn lease, Worker B tiếp quản, Worker A gửi failure muộn -> Token B và trạng thái của Worker B được bảo toàn tuyệt đối.
  3. *Race 3:* Worker A hết hạn lease, Worker B tiếp quản, Worker A gửi success muộn -> Thao tác của Worker A bị từ chối, bản ghi không bị chuyển `DELETED` sai quy trình.
  4. *Race 4:* Media đã được Worker B hoàn tất `DELETED`, Worker A gửi failure muộn -> Bản ghi giữ nguyên trạng thái `DELETED`, không bị chuyển thành `FAILED`.
  5. *Race 5:* User DELETE trong khi Worker đang giữ reconciliation lease active -> Request xử lý idempotent, lease của worker không bị xóa hay ghi đè.
  6. *Race 6:* Reconciliation worker chạy trong khi User DELETE đang in-flight -> Worker không thể chiếm đoạt lease của User DELETE.
  7. *Race 7:* Worker 1 xóa Storage thành công nhưng crash trước DB checkpoint -> Lease hết hạn, Worker 2 tiếp quản gọi delete idempotent (404 no-op) và commit `DELETED` thành công.
  8. *Race 8:* Upload timeout ban đầu, compensation delete 404, object xuất hiện muộn -> Background worker tìm thấy bản ghi PENDING, dọn dẹp orphan object khỏi Storage và commit tombstone `DELETED`.
  9. *Race 9:* Concurrent giữa `markReady()` và `beginReconciliation()` trên cùng một PENDING media -> Đúng một bên thành công, loại trừ lẫn nhau hoàn toàn.
  10. *Race 10:* Concurrent giữa User DELETE và Worker delete failure -> Lỗi muộn từ worker không ghi đè trạng thái của User DELETE.

#### FIX D — WebP Bitstream Dimensions Verification Before Raster Decode
- **Xác thực cấu trúc bitstream trước giải mã raster:**
  - Đọc và xác thực kích thước canvas từ chunk `VP8X` (nếu có).
  - Luôn đọc và phân tích kích thước thực tế từ bitstream chunk `VP8 ` hoặc `VP8L`.
  - So khớp nghiêm ngặt: Nếu có `VP8X`, kích thước canvas và kích thước bitstream frame bắt buộc phải trùng khớp hoàn toàn. Từ chối ngay lập tức nếu có sự chênh lệch (chống decompression bomb / canvas spoofing).
  - Áp dụng giới hạn `width <= 10,000`, `height <= 10,000`, và `totalPixels <= 25,000,000` (25MP) cho cả canvas và bitstream trước bất kỳ thao tác giải mã nào.
  - Tuyệt đối không gọi `ImageIO.read()` đối với các tệp vượt quá ngưỡng hoặc có cấu trúc bất thường.

#### FIX E — EXIF/TIFF Fail-Closed Parser & Metadata Verification
- **Orientation Parser:**
  - Phân biệt rõ ràng giữa ảnh không có EXIF (mặc định 1) và ảnh có EXIF bị lỗi.
  - Bắt buộc kiểm tra: Header TIFF tối thiểu 8 bytes, endianness (`II` hoặc `MM`), magic number `42`, offset IFD0 hợp lệ trong phạm vi buffer, số lượng entries hợp lệ.
  - Tag `0x0112` (Orientation): Xác thực kiểu dữ liệu SHORT (3) hoặc LONG (4), count = 1, giá trị bắt buộc thuộc khoảng $1..8$. Từ chối mọi giá trị ngoài phạm vi hoặc malformed header bằng `ValidationException` (không coi lỗi là Orientation 1).
- **Metadata Verification Sau Xử Lý:**
  - Kiểm tra toàn diện `ExifIFD0Directory` (loại bỏ Make, Model, DateTime, Orientation, Software).
  - Kiểm tra `ExifSubIFDDirectory`, `GpsDirectory`, `XmpDirectory`, `IptcDirectory`.
  - Mọi exception xảy ra trong quá trình đọc metadata đều fail-closed (từ chối tệp).
  - Đối với WebP: Thực hiện structural verification trên RIFF container, chứng minh không còn chunk EXIF, XMP, IPTC và các cờ tương ứng trong VP8X đã được xóa về 0.
