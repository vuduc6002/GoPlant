### 2. CHI TIẾT CÁC HẠNG MỤC SỬA LỖI (FIX A - F)

#### FIX A — Scheduled Reconciliation Activation
- **Đóng gói Configuration:** Khởi tạo `SchedulingConfig.java` với `@EnableScheduling` và `@ConditionalOnProperty(name = "media.reconciliation.scheduling.enabled", havingValue = "true", matchIfMissing = true)`.
- **Cấu hình môi trường:**
  - `backend/src/main/resources/application.properties`: Khai báo `media.reconciliation.scheduling.enabled=true`, `initial-delay-ms=60000`, `fixed-delay-ms=900000` (15 phút), `safety-window-seconds=300`, `batch-size=50`, `lease-duration-seconds=60`, `max-attempts=5`, `base-backoff-seconds=30`.
  - `backend/src/test/resources/application.properties`: Tắt mặc định `media.reconciliation.scheduling.enabled=false` để tránh can nhiễu các bộ test khác.
- **Kiểm thử tự động:** `MediaReconciliationSchedulingTest.java` chứng minh task scheduling được đăng ký khi `enabled=true` và cấu hình injection chính xác.

#### FIX B — Atomic State Machine & Reconciliation Leases
- **Flyway Migration V3 (`V3__media_reconciliation_leases.sql`):**
  - Cập nhật ràng buộc `media_objects_status_check` hỗ trợ: `PENDING`, `READY`, `ATTACHED`, `DELETING`, `DELETED`, `RECONCILING`, `FAILED`.
  - Bổ sung các cột phân tán: `lease_token VARCHAR(64)`, `lease_expires_at TIMESTAMPTZ`, `attempt_count INT DEFAULT 0 NOT NULL`, `last_attempt_at TIMESTAMPTZ`, `next_retry_at TIMESTAMPTZ`, `error_detail VARCHAR(1000)`.
  - Tạo chỉ mục tối ưu hóa batch query: `idx_media_objects_reconciliation (status, created_at, next_retry_at, lease_expires_at)`.
- **Bảo vệ `markReady()`:**
  - Áp dụng `findByIdForUpdate` (pessimistic lock) trên hàng media.
  - Kiểm tra trạng thái nghiêm ngặt: chỉ cho phép chuyển sang `READY` khi trạng thái hiện tại là `PENDING` và không có lease nào đang hoạt động.
  - Từ chối ngay lập tức với `IllegalStateException` nếu media đang ở trạng thái `RECONCILING`, `DELETING`, `DELETED`, `FAILED` hoặc đang bị worker lease.
- **Điều phối Reconciliation Phân tán (`MediaTransactionCoordinator` & `MediaReconciliationService`):**
  - `beginReconciliation()`: Khóa dòng bằng `findByIdForUpdate`, chuyển `PENDING` sang `RECONCILING`, cấp `lease_token` và `lease_expires_at` trong transaction độc lập (`REQUIRES_NEW`) trước khi thực hiện HTTP I/O ra Storage.
  - Tuyệt đối bảo vệ: Nếu media đã ở trạng thái `READY` hoặc `ATTACHED`, reconciliation bỏ qua (trả về null), không bao giờ xóa nhầm object hợp lệ.
  - Storage delete được thực thi bên ngoài database transaction.
  - Sau khi storage delete thành công: `completeReconciliationSuccess()` chuyển status sang `DELETED` và dọn dẹp lease.
  - Nếu storage delete thất bại: `recordReconciliationFailure()` tăng `attempt_count`, áp dụng exponential backoff (`next_retry_at`), lưu thông tin lỗi đã làm sạch secret (`error_detail`), và chuyển sang `FAILED` khi đạt `maxAttempts` (ngăn vòng lặp vô tận).
  - Batching: `findStuckMediaForReconciliation` sử dụng `Pageable` phân trang an toàn.
- **10 Kịch bản Race Tests (`MediaReconciliationRaceTest.java`):**
  1. *Race 1:* Upload timeout theo sau bởi late Supabase processing — PENDING được lưu giữ và worker dọn dẹp thành công.
  2. *Race 2:* Worker claim lease PENDING, thread upload gọi concurrent `markReady()` — `markReady()` bị từ chối fail-closed.
  3. *Race 3:* 2 worker chạy reconciliation đồng thời — đúng 1 worker claim được lease, worker 2 bị từ chối.
  4. *Race 4:* Xóa ban đầu gặp 404, object xuất hiện muộn — reconciliation dọn dẹp triệt để.
  5. *Race 5:* Worker tiến trình chết sau khi claim nhưng trước khi xóa — worker khác claim lại sau khi lease hết hạn.
  6. *Race 6:* Worker chết sau khi xóa storage nhưng trước checkpoint DB — lần chạy tiếp theo hoàn tất tombstone `DELETED`.
  7. *Race 7:* Xóa storage thất bại — retry theo exponential backoff và đánh dấu `FAILED` khi vượt quá `maxAttempts`.
  8. *Race 8:* Media ở trạng thái `READY` hoặc `ATTACHED` — worker không bao giờ xóa.
  9. *Race 9:* Người dùng xóa media trong lúc worker đang xử lý — trạng thái `DELETED` được bảo toàn an toàn.
  10. *Race 10:* Bất biến: Không bao giờ tồn tại trạng thái `READY` trỏ tới object đã bị xóa khỏi storage.

#### FIX C — Strict WebP RIFF Validation Before Raster Decode
- **Kiểm tra Container RIFF:**
  - Xác thực magic bytes `RIFF` và `WEBP`.
  - Xác thực độ dài container khai báo: `declaredRiffSize + 8 == webpBytes.length` (ngăn trailing bytes hoặc truncated files).
- **Phân tích Chunks nội bộ:**
  - Duyệt tuần tự từng chunk theo offset chính xác, đảm bảo kích thước chunk không vượt quá biên container RIFF (`chunkOffset + 8 + paddedChunkSize <= riffEnd`).
  - Kiểm tra chunk header & payload tối thiểu: `VP8X` (>= 10B), `VP8 ` (>= 10B và kiểm tra 3 bytes signature `0x9D 0x01 0x2A`), `VP8L` (>= 5B và kiểm tra signature `0x2F`).
  - Từ chối animated WebP (cờ animation trong VP8X hoặc chunk `ANIM`/`ANMF`).
  - Ngăn chặn file chứa nhiều chunk hình ảnh (chỉ cho phép duy nhất 1 frame tĩnh).
- **Ràng buộc Kích thước Trước Raster Decode:**
  - Đọc dimensions trực tiếp từ VP8/VP8L/VP8X header và kiểm tra kích thước: chiều rộng, chiều cao <= 10,000 px, tổng diện tích <= 25,000,000 pixels (25 MP) TRƯỚC KHI gọi `ImageIO.read()`.
- **Phân tích EXIF Orientation An toàn:**
  - Tự xây dựng parser TIFF IFD0 đọc tag `0x0112` (Orientation) thuần Java, độc lập với file container.
  - Từ chối orientation giá trị 0 hoặc nằm ngoài 1..8 với `ValidationException`.
  - Đối với WebP: từ chối fail-closed nếu orientation > 1 để bảo vệ raster decoder.
  - Chỉ gọi `ImageIO.read()` giải nén raster sau khi toàn bộ container và kích thước hợp lệ.

#### FIX D — Frontend Multipart Interceptor
- **Hàm `cleanMultipartFormDataHeaders`:** Trích xuất logic phát hiện `FormData` (hỗ trợ cả `instanceof FormData` và Duck Typing `{ append: Function }`), xóa bỏ triệt để header `Content-Type: multipart/form-data` thủ công.
- **Vị trí thực thi:** Đặt tại đầu Request Interceptor trong `apiClient.ts`, TRƯỚC các nhánh trả về sớm (`isPublic`, `hasExpectedUserId`).
- **Hỗ trợ đa định dạng Headers:** Xử lý tương thích cả `AxiosHeaders` instance (qua `.delete()`) và plain JavaScript object.
- **Bảo toàn bảo mật:** Giữ nguyên header `Authorization: Bearer <token>`, session generation guard và session user mismatch protection.
- **Kiểm thử tự động:** Bổ sung test suite chứng minh header được làm sạch, boundary được runtime tự động sinh, và session mismatch bị chặn trước network.

#### FIX E & F — Configuration, HTTPS Signed URL & Safe Logging
- **Single Source of Truth cho Max File Size:** `ImageMetadataProcessor` inject trực tiếp `SupabaseStorageProperties.getMaxFileSizeBytes()`, áp trần cứng bảo vệ tối đa 5MB (`5 * 1024 * 1024`).
- **Ép buộc HTTPS:** `SupabaseStorageGateway.resolveFullSignedUrl()` xác thực base URL bắt buộc phải là HTTPS; từ chối HTTP, từ chối external hosts, từ chối userinfo (`@`), từ chối protocol-relative URLs (`//`).
- **Parser JWT RFC 7519 Chuẩn:** Sử dụng `com.nimbusds.jwt.JWTParser` từ thư viện `nimbus-jose-jwt` để kiểm tra cấu trúc JWT payload, yêu cầu chính xác claim `role="service_role"`, từ chối `anon`, `authenticated` hoặc payload JSON sai định dạng.
- **Log Sanitization Triệt Để:** `sanitizeLogMessage()` làm sạch tự động các sensitive fields: `apikey`, `Authorization: Bearer`, `password`, `access_token`, `refresh_token`, `secret`, và các query parameters nhạy cảm trên URL (`?token=...`).
