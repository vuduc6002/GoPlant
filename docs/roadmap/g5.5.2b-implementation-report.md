## 1. Executive Summary & Context

Giai đoạn **G5.5.2b** thiết lập hạ tầng lưu trữ tệp tin đa phương tiện riêng tư và đường ống tải ảnh an toàn (Secure Image Upload Pipeline) cho hệ thống GoPlant. Đây là phân hệ nền tảng then chốt mở đường cho tính năng đính kèm ảnh đa phân hệ (G5.5.3) và chẩn đoán sâu bệnh cây trồng bằng AI (G5.5.5).

Trước G5.5.2b, hệ thống lưu trữ URL dạng chuỗi thô trong các bảng thực thể (`users.avatar_url`, `gardens.cover_image_url`, `user_plants.image_url`, `care_logs.image_urls`, `growth_journals.image_urls`, `plant_species.thumbnail_url`) mà chưa có cơ chế kiểm duyệt nội dung, chuẩn hóa metadata, lọc bỏ dữ liệu nhạy cảm hay ngăn chặn tấn công SSRF.

Phân hệ G5.5.2b đã hoàn thành 100% các mục tiêu kỹ thuật:
1. **Thiết kế và thực thi Flyway Migration V2 (`V2__media_objects.sql`):** Bổ sung bảng `media_objects` quản lý vòng đời tệp tin trong Private Bucket với đầy đủ ràng buộc toàn vẹn, kích thước, trạng thái và chỉ mục tối ưu.
2. **Triển khai Backend Multipart Proxy:** Khách hàng Frontend tải ảnh trực tiếp lên Backend GoPlant qua `POST /api/v1/media`, không tiếp xúc trực tiếp và không bao giờ nắm giữ Supabase Service Role Key.
3. **Pipeline xử lý ảnh và bóc tách EXIF bằng mã nguồn Java thuần túy:** Kiểm tra magic bytes (JPEG, PNG, WebP), giải mã kích thước an toàn (chặn decompression bombs > 10,000px / 25MP), tự động xoay chuẩn theo orientation tag, loại bỏ toàn bộ dữ liệu vị trí GPS/thiết bị/camera, chặn WebP animation (chống DoS), và tính toán mã băm SHA-256 xác thực toàn vẹn.
4. **Bộ xác thực an toàn `MediaUrlValidator`:** Ngăn chặn triệt để tấn công SSRF, cấm các scheme nguy hiểm (`file:`, `data:`, `content:`, `javascript:`), cấm thông tin đăng nhập trong URL, cấm IP loopback/RFC1918/link-local/multicast/IPv6-mapped và tên miền nội bộ trên toàn bộ 7 service hiện có.
5. **Cơ chế cấp Signed Read URL tạm thời:** Cấp URL đọc có chữ ký số hết hạn trong 300 giây qua `GET /api/v1/media/{mediaId}/read-url` với kiểm tra nghiêm ngặt quyền sở hữu `ownerId`.
6. **Xóa tệp tin có kiểm soát Idempotent & Bảo vệ liên kết:** `DELETE /api/v1/media/{mediaId}` từ chối xóa tệp đang ở trạng thái `ATTACHED` với mã lỗi `409 Conflict` (`MEDIA_ATTACHED`), đồng thời xử lý xóa compensation an toàn.
7. **Frontend Media Client & Hooks Module:** Xây dựng module `frontend/src/features/media` hoàn chỉnh với client-side validation, React Query hooks có cô lập phiên (`userId`), staleTime 4 phút và xóa cache tức thì khi xóa ảnh.

## 3. Database Migration V2 & Schema Verification

Tệp migration: `backend/src/main/resources/db/migration/V2__media_objects.sql`

```sql
CREATE TABLE IF NOT EXISTS media_objects (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    owner_id UUID NOT NULL REFERENCES users(id) ON DELETE RESTRICT,
    bucket VARCHAR(100) NOT NULL,
    object_key VARCHAR(500) NOT NULL,
    mime_type VARCHAR(100) NOT NULL,
    size_bytes BIGINT NOT NULL,
    sha256 CHAR(64) NOT NULL,
    width INTEGER NULL,
    height INTEGER NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'PENDING',
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    CONSTRAINT media_objects_size_bytes_check CHECK (size_bytes >= 1 AND size_bytes <= 5242880),
    CONSTRAINT media_objects_status_check CHECK (status IN ('PENDING', 'READY', 'ATTACHED', 'DELETING', 'DELETED')),
    CONSTRAINT uq_media_objects_bucket_key UNIQUE (bucket, object_key)
);

CREATE INDEX IF NOT EXISTS idx_media_objects_owner_created ON media_objects(owner_id, created_at DESC);
CREATE INDEX IF NOT EXISTS idx_media_objects_status ON media_objects(status);
```

### Điểm kiểm tra Schema:
1. **Kiểu dữ liệu & Độ dài khớp Entity:**
   - `id`: UUID (Hibernate auto-generation)
   - `bucket`: `VARCHAR(100)`
   - `object_key`: `VARCHAR(500)`
   - `mime_type`: `VARCHAR(100)`
   - `sha256`: `CHAR(64)`
   - `status`: `VARCHAR(20)`
2. **Khóa ngoại & Toàn vẹn:** `owner_id` tham chiếu `users(id)` với `ON DELETE RESTRICT` để ngăn xóa tài khoản người dùng khi còn tệp tin media chưa dọn dẹp.
3. **Ràng buộc Check Constraints:**
   - `media_objects_size_bytes_check`: bắt buộc `size_bytes BETWEEN 1 AND 5242880` (5MB).
   - `media_objects_status_check`: chỉ chấp nhận các trạng thái hợp lệ trong enum `MediaStatus`.
4. **Xác minh kiểm thử tự động:** `DatabaseSchemaIntegrationTest.java` đã xác minh V1 + V2 với 12 bảng, 18 foreign keys, 15 check constraints, 21 indexes trên PostgreSQL 16.

## 4. Supabase Storage Integration & Gateway Design

- **Lớp Gateway:** `SupabaseStorageGateway.java`
- **Mô hình tương tác:** Sử dụng Spring Boot `RestClient` với cấu hình HTTP timeouts (5 giây connect timeout, 15 giây read timeout) thông qua `RestClientConfig.java`.
- **Cấu hình thuộc tính:** `SupabaseStorageProperties.java`
  - `supabase.storage.url`: URL trỏ tới Supabase Storage REST API (`https://<project-ref>.supabase.co/storage/v1`).
  - `supabase.storage.api-key`: Service Role Key (hoặc API Key quản trị), chỉ cấu hình tại backend qua biến môi trường `SUPABASE_SERVICE_ROLE_KEY` / `SUPABASE_STORAGE_API_KEY`.
  - `supabase.storage.bucket`: `goplant-private-media` (mặc định private bucket).
  - `supabase.storage.max-file-size-bytes`: `5242880` (5MB).
  - `supabase.storage.signed-url-ttl-seconds`: `300` (5 phút).
- **Thao tác Gateway:**
  - `upload(bucket, objectKey, bytes, mimeType)`: gửi `POST /object/{bucket}/{objectKey}` với header `x-upsert: false`.
  - `createSignedUrl(bucket, objectKey, expiresInSeconds)`: gửi `POST /object/sign/{bucket}/{objectKey}` trả về URL chứa token ký tạm thời.
  - `delete(bucket, objectKey)`: gửi `DELETE /object/{bucket}` với mảng `prefixes: [objectKey]`. Xử lý idempotent (coi 404 là thành công).
- **Bảo đảm không rò rỉ Key:** Toàn bộ request log và exceptions được lọc sạch, không log header `Authorization` hoặc `apikey`.

## 5. Backend Multipart Proxy Architecture

Hệ thống tuân thủ nghiêm ngặt nguyên tắc **Zero Client Trust & Backend Multipart Proxy**:
- Frontend **không kết nối trực tiếp** tới Supabase Storage.
- Frontend gửi multipart POST lên endpoint của GoPlant: `/api/v1/media`.
- Backend nhận luồng stream, xác thực JWT, kiểm tra quota/dung lượng, tiền xử lý và bóc tách metadata, sau đó đại diện người dùng upload vào Private Bucket.
- Nhờ mô hình Proxy, hệ thống hoàn toàn chủ động trong việc xoay ảnh, loại bỏ EXIF nhạy cảm, chặn virus/tệp độc hại và kiểm soát quyền truy cập trước khi tệp chạm tới kho lưu trữ.

## 6. Image Processing, EXIF Stripping & Transformation Pipeline

- **Lớp xử lý chính:** `ImageMetadataProcessor.java`
- **Thư viện tích hợp thuần Java (không phụ thuộc ImageMagick/Native binaries):**
  - `metadata-extractor:2.19.0`: phân tích các khối EXIF Segment (IFD0, SubIFD, GPS).
  - `imageio-webp:3.12.0` (TwelveMonkeys): giải mã và mã hóa WebP SPI.
- **Quy trình xử lý tuần tự 7 bước:**
  1. **Magic Bytes Detection:** Kiểm tra byte header thực tế, từ chối dựa vào extension hoặc Content-Type do client gửi lên.
     - JPEG: `0xFF, 0xD8, 0xFF`
     - PNG: `0x89, 0x50, 0x4E, 0x47`
     - WebP: `0x52, 0x49, 0x46, 0x46` (RIFF) + offset 8 `0x57, 0x45, 0x42, 0x50` (WEBP)
  2. **Dung lượng:** Kiểm tra `size <= 5MB` và `size > 0`.
  3. **Chống Decompression Bomb & Animation DoS:**
     - Giới hạn kích thước tối đa: 10,000 px mỗi chiều, diện tích <= 25,000,000 px (25 Megapixels).
     - Đối với WebP: kiểm tra cờ `ANIM` chunk và `ANMF` chunk. Nếu là ảnh động, lập tức từ chối với lỗi `VALIDATION_ERROR` (chỉ chấp nhận ảnh tĩnh).
  4. **Orientation Correction:** Đọc thẻ Orientation từ EXIF IFD0 (giá trị 1..8). Thực hiện phép biến đổi affine tương ứng (`AffineTransform` rotate 90°, 180°, 270° hoặc flip) để đưa hình ảnh về trạng thái thẳng đứng trước khi gỡ thẻ EXIF.
  5. **Metadata Stripping:**
     - Với JPEG và PNG: ghi lại hình ảnh qua `ImageIO.write` sạch vào bộ đệm bộ nhớ mới, loại bỏ hoàn toàn các segment metadata gốc.
     - Với WebP: thực hiện cắt lọc RIFF chunk ở mức byte, chỉ giữ lại header RIFF/WEBP và khối dữ liệu ảnh tĩnh (VP8, VP8L, VP8X), loại bỏ sạch khối `EXIF` chunk và `XMP ` chunk.
  6. **Post-Stripping Verification:** Đọc lại mảng byte đầu ra qua `ImageMetadataReader.readMetadata()`, khẳng định không còn thẻ `GpsDirectory`, `TAG_DATETIME_ORIGINAL`, `TAG_MAKE`, hay `TAG_MODEL`.
  7. **Mã băm SHA-256:** Tính toán mã băm SHA-256 trên mảng byte đã làm sạch để lưu vào database phục vụ kiểm tra trùng lặp và tính toàn vẹn.

## 8. Error Handling & RFC 7807 Exception Mapping

Hệ thống sử dụng bộ mã lỗi chuẩn hóa đóng gói trong envelope `ApiResponse`:
- `400 Bad Request` -> `VALIDATION_ERROR`: Định dạng ảnh không hỗ trợ, ảnh lỗi, URL vi phạm SSRF, hoặc tham số ID rỗng.
- `401 Unauthorized` -> `UNAUTHORIZED`: Thiếu hoặc hết hạn JWT Bearer token.
- `403 Forbidden` -> `FORBIDDEN`: Người dùng B cố ý truy cập hoặc xóa media của Người dùng A.
- `404 Not Found` -> `RESOURCE_NOT_FOUND`: `mediaId` không tồn tại trong hệ thống.
- `409 Conflict` -> `MEDIA_ATTACHED`: Xóa tệp phương tiện đang ở trạng thái `ATTACHED` (có `field: "mediaId"`).
- `413 Payload Too Large` -> `FILE_TOO_LARGE`: Dung lượng tệp vượt quá 5MB.
- `503 Service Unavailable` -> `STORAGE_UNAVAILABLE`: Sự cố kết nối hoặc lỗi dịch vụ từ Supabase Storage Gateway.

## 12. React Query Hooks, Caching & Session Isolation

- **Query Key chuẩn hóa:**
  - `queryKeys.media.all(userId)`: `['media', userId]`
  - `queryKeys.media.readUrl(userId, mediaId)`: `['media', userId, 'read-url', mediaId]`
- **Thời gian Cache:** `staleTime: 4 * 60 * 1000` (4 phút). Do signed URL của backend hết hạn sau 5 phút (300s), việc đặt staleTime 4 phút bảo đảm client không bao giờ tái sử dụng một URL sắp hết hạn.
- **Cô lập phiên đăng nhập:** Khi người dùng đổi tài khoản từ User A sang User B, query cache của User A tự động bị cô lập, không tái sử dụng cho User B.
- **Dọn dẹp Mutation:** `useDeleteMediaMutation` chủ động gọi `queryClient.removeQueries({ queryKey: queryKeys.media.readUrl(ownerUserId, mediaId) })` ngay khi xóa thành công.

## 19. Storage Cleanup, Idempotency & Compensation Logic

- **Compensation khi tải lên thất bại:** Nếu gửi dữ liệu sang Supabase Storage thất bại, bản ghi `media_objects` ở trạng thái `PENDING` được xóa ngay lập tức (`rollback pending record`), tránh để lại rác trong database.
- **Compensation khi cập nhật READY thất bại:** Nếu tải lên storage thành công nhưng cập nhật database thất bại, gateway thực thi compensation delete để xóa file rác khỏi storage bucket.
- **Idempotency khi xóa:** Xóa một tệp tin đã ở trạng thái `DELETED` trả về `200 OK` thành công, không báo lỗi giả.

## 20. Cross-User Privacy & Ownership Protection

- **Kiểm soát quyền truy cập chặt chẽ:**
  - `GET /api/v1/media/{mediaId}/read-url`: Chỉ cấp URL khi `media.owner.id == currentUserId`. Nếu không khớp, trả về `403 Forbidden` (`FORBIDDEN`).
  - `DELETE /api/v1/media/{mediaId}`: Chỉ chủ sở hữu mới có quyền yêu cầu xóa.
  - Object Key trong Storage được định dạng theo cấu trúc không gian tên: `{ownerId}/{randomUUID}.{ext}`, hoàn toàn ngăn chặn việc ghi đè hoặc xung đột giữa các người dùng.

## 22. Deviations, Challenges & Resolutions

1. **Vấn đề Hibernate Detached Entity trong `MediaService.uploadMedia`:**
   - *Thách thức:* Việc gán thủ công `media.setId(UUID.randomUUID())` trước khi gọi `save()` khiến Hibernate hiểu nhầm là entity detached và thực thi `merge()`, gây ra `OptimisticLockingFailureException`.
   - *Giải pháp:* Tách riêng UUID của Object Key lưu trữ với ID của entity. Entity ID được để Hibernate tự sinh khi gọi `save()`, bảo đảm quy trình `persist()` chuẩn xác.
2. **Vấn đề Constructor Ambiguity và Mockito `@InjectMocks`:**
   - *Thách thức:* Khi thêm constructor chứa `MediaUrlValidator`, Mockito inject null khi chạy các unit test cũ (`CareLogServiceTest`, `GrowthJournalServiceTest`).
   - *Giải pháp:* Thiết lập cơ chế fallback an toàn: `this.mediaUrlValidator = mediaUrlValidator != null ? mediaUrlValidator : new MediaUrlValidator("https")` trên toàn bộ 7 service.
3. **WebP ImageIO Parsing:**
   - *Thách thức:* Một số tệp WebP thử nghiệm thiếu VP8 header tiêu chuẩn gây lỗi khi ImageIO đọc.
   - *Giải pháp:* Xây dựng bộ parser container RFC 6386 thuần Java đọc trực tiếp kích thước từ các chunk `VP8X`, `VP8`, `VP8L`, đồng thời kiểm tra cờ animation trước khi chuyển qua ImageIO.
