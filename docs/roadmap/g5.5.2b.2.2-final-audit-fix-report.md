### 2. CHI TIẾT CÁC HẠNG MỤC TRIỂN KHAI (FIX A - D)

#### FIX A — Loại Bỏ Toàn Bộ Tokenless State Transitions
- **File sửa đổi:** `backend/src/main/java/com/cmc/plant_care_backend/service/MediaTransactionCoordinator.java`
- **Các hàm và constructor đã xóa bỏ hoàn toàn:**
  - `completeDelete(UUID mediaId)`: Loại bỏ overload không có deleteToken.
  - `completeReconciliation(UUID mediaId)`: Loại bỏ overload không có leaseToken.
  - `DeleteDecision.ofProceed(String bucket, String objectKey)`: Loại bỏ overload không mang token.
  - Constructor `ReconciliationCandidate(UUID, String, String, MediaStatus)`: Loại bỏ constructor cho phép `leaseToken = null`.
- **Ràng buộc nghiêm ngặt cho 4 hàm cập nhật trạng thái:**
  1. `completeDelete(UUID mediaId, String deleteToken)`: Token không rỗng, trùng khớp chính xác với `media.getLeaseToken()`, trạng thái bắt buộc là `DELETING`.
  2. `recordDeleteFailure(UUID mediaId, String deleteToken, String errorMessage)`: Token không rỗng, trùng khớp chính xác DB, trạng thái bắt buộc là `DELETING`.
  3. `completeReconciliationSuccess(UUID mediaId, String leaseToken)`: Token không rỗng, trùng khớp chính xác DB, trạng thái bắt buộc là `RECONCILING` hoặc `DELETING`.
  4. `recordReconciliationFailure(UUID mediaId, String leaseToken, String errorMessage, int maxAttempts, Duration baseBackoff)`: Token không rỗng, trùng khớp chính xác DB, trạng thái bắt buộc là `RECONCILING` hoặc `DELETING`.
- **Bảo vệ bất biến (Invariant Protection):**
  - Tuyệt đối không cho phép bất kỳ callback muộn nào thay đổi hoặc can nhiễu vào các bản ghi đang ở trạng thái `READY`, `ATTACHED`, `DELETED`, hoặc `FAILED`.
- **Bộ test bổ sung trong `MediaTransactionCoordinatorTest.java`:**
  - Kiểm thử `null` token, empty string `""`, whitespace `"   "`, mismatched token, stale token của Worker A sau khi Worker B tiếp quản, stale token khi bản ghi đã `DELETED`, và gọi trên các trạng thái được bảo vệ.
  - Khẳng định trạng thái, token, expiry, attempt count, retry time, và error detail không bị sửa sai và không gọi `saveAndFlush`.

  - **Nhóm 1: Real Multi-threaded Concurrent Race Tests (Đa luồng thực sự với CountDownLatch & Gateway Hooks):**
    1. *Race 1:* Hai worker đồng thời gọi `coordinator.beginReconciliation()` qua `readyLatch` và `startLatch` -> Đúng 1 worker chiếm được lease, worker còn lại nhận null.
    2. *Race 5:* User DELETE trong lúc reconciliation worker thực sự đang bị tạm dừng bên trong `storageGateway.delete()` -> User delete phát hiện active reconciliation lease và xử lý idempotent (không gọi delete lặp, không xóa lease, không lỗi); worker hoàn tất xóa object và commit `DELETED`.
    3. *Race 6:* Reconciliation worker chạy trong lúc User DELETE đang bị tạm dừng bên trong `storageGateway.delete()` -> Worker không thể chiếm đoạt lease của User DELETE (trả về 0 candidate); user delete hoàn tất xóa và commit `DELETED`.
    4. *Race 9:* Đồng thời thực thi `markReady()` và `beginReconciliation()` qua `readyLatch`/`startLatch` -> Loại trừ lẫn nhau hoàn toàn (đúng 1 thao tác thành công).
    5. *Race 10:* User DELETE và stale worker failure callback thực thi đồng thời -> User DELETE hoàn tất thành công, callback lỗi muộn bị từ chối, DB chuyển `DELETED`.
  - **Nhóm 2: Controlled Interleaving & Crash Recovery Tests (Kiểm thử vòng đời và phục hồi lỗi tuần tự có kiểm soát):**
    6. *Scenario 2:* Worker A hết hạn lease, Worker B tiếp quản, Worker A gửi failure muộn -> Token B và trạng thái `RECONCILING` được bảo toàn.
    7. *Scenario 3:* Worker A hết hạn lease, Worker B tiếp quản, Worker A gửi success muộn -> Success muộn bị từ chối, bản ghi không bị chuyển `DELETED` sai quy trình.
    8. *Scenario 4:* Media đã được Worker B hoàn tất `DELETED`, Worker A gửi failure muộn -> Bản ghi giữ nguyên `DELETED`, không bị chuyển thành `FAILED`.
    9. *Scenario 7:* Worker 1 xóa Storage thành công nhưng crash trước DB checkpoint -> Lease hết hạn, Worker 2 chạy `reconcileStuckMedia()`, gọi delete Storage nhận kết quả 404/idempotent và commit `DELETED`.
    10. *Scenario 8:* Upload timeout ban đầu, compensation delete trả 404, object xuất hiện muộn -> `reconcileStuckMedia()` phát hiện bản ghi PENDING quá hạn, dọn dẹp orphan object và commit tombstone `DELETED`.

#### FIX C — WebP Metadata Verifier Fail-Closed
- **File:** `backend/src/main/java/com/cmc/plant_care_backend/common/media/ImageMetadataProcessor.java`
- **Hàm:** `verifyNoSensitiveWebPMetadata(byte[] webpBytes)`
- **Các cải tiến nghiêm ngặt:**
  1. Kiểm tra magic container: `RIFF....WEBP`.
  2. Bắt buộc tuyệt đối: `declaredRiffSize + 8L == (long) webpBytes.length`. Loại bỏ hoàn toàn `Math.min()`.
  3. Duyệt từng chunk:
     - Header tối thiểu 8 bytes trong container.
     - `chunkSize` không âm và `offset + 8 + chunkSize` không vượt quá chiều dài container.
     - Tính toán padding byte nếu `chunkSize` lẻ, xác nhận `nextOffset <= riffEndOffset`.
  4. Từ chối ngay lập tức khi phát hiện chunk `EXIF`, `XMP ` hoặc cờ EXIF/XMP trong `VP8X`.
  5. Sau khi kết thúc vòng lặp, kiểm tra chính xác `offset == riffEndOffset`. Bất kỳ dữ liệu thừa nào sau chunk cuối cùng đều ném `ValidationException`.
- **Bộ kiểm thử bổ sung trong `ImageMetadataProcessorTest.java` (71 tests):**
  - Clean WebP passes.
  - RIFF size nhỏ hơn dữ liệu (dữ liệu thừa / payload giấu).
  - RIFF size lớn hơn dữ liệu (khai báo vượt).
  - Truncated chunk header.
  - Chunk size vượt quá container boundary.
  - Chunk lẻ thiếu padding byte.
  - Chunk lẻ có padding byte hợp lệ.
  - Chunk EXIF bị từ chối.
  - Chunk XMP bị từ chối.
  - VP8X EXIF flag bit bật bị từ chối.
  - VP8X XMP flag bit bật bị từ chối.
